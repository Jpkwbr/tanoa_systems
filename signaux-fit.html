Signaux de fit

Indices pour qualifier un besoin en découverte / premier contact. Un seul service ou connecteur suffit s’il entre dans une catégorie verte. Décision go / no-go : grille 02-evaluation-mission (ce document ne la remplace pas).

Usage interne. Ne pas envoyer au client. Synthèse aussi en annexe de la grille 02.

Lecture

Vert · jaune · rouge

  • Vert — approfondir ; forfait bornable probable.
  • Jaune — reformuler ou borner avant tout devis.
  • Rouge — écarter, ou reformuler jusqu’à sortir du rouge.

Verts

Approfondir

Applications / outils qui doivent se parler

  • « On exporte un CSV du LIMS, quelqu’un le retape dans l’ERP. »
  • « Deux logiciels métier : on copie-colle des identifiants. »
  • « Des fichiers arrivent sur un partage / FTP ; on ne sait pas si le traitement a réussi. »
  • « Il faut brancher un outil de labo / un automate / une API partenaire sur le SI. »
  • « Les données divergent entre A et B ; on s’en aperçoit trop tard. »

Traitements asynchrones, files, jobs fragiles

  • « Un batch de nuit plante ; on le relance à la main. »
  • « Les imports bloquent l’interface pendant longtemps. »
  • « Des événements arrivent en rafale ; on en perd sans le savoir. »
  • « Quand une commande est validée, plusieurs systèmes doivent réagir sans s’attendre en chaîne. »
  • « On a une file, mais personne n’est prévenu quand elle sature ou échoue. »

Travaux périodiques / polling

  • « Toutes les X minutes on interroge une source et on pousse les nouveautés. »
  • « Réconciliation horaire ou quotidienne entre deux référentiels. »
  • « Surveiller une condition métier (échéance, quota, état) et déclencher une action. »

Fiabiliser / industrialiser une petite chaîne de services

  • « Ça marche en démo, sans reprises ni tests. »
  • « Chaque nouveau flux est un script one-shot. »
  • « On veut un modèle commun pour démarrer, configurer et faire tourner quelques workers. »
  • « On a déjà des services ; on veut les rendre fiables et observables ensemble. »

Être prévenu quand un flux ou un service demande une action

  • « Personne n’est alerté tant qu’un utilisateur ne s’en plaint. »
  • « Notification si le connecteur échoue plusieurs fois de suite. »
  • « Des règles différentes selon la gravité et les destinataires. »
  • « Pouvoir brancher d’autres sources d’alerte plus tard sans tout reconstruire. »

Conditions commerciales (toujours)

  • Décideur technique joignable ; besoin exprimable en lots.
  • Client ouvert au forfait + critères d’acceptation.
  • Phase 0 : charge du lot 1 compatible avec la dispo.

Jaunes

Cadrer fort avant devis

SignalExempleLecture
Demande vague « Digitaliser » ; « moderniser toute la plateforme » Recadrer 1–2 flux concrets, ou no-go
Solution imposée « Il nous faut Kafka / microservices / l’outil X » Repartir du besoin métier
API HTTP comme besoin principal « Une API REST / un CRUD, c’est le projet » Peu de terrain différenciant. Vert seulement si l’HTTP est la porte d’entrée d’un flux (callback → traitement → système métier + fiabilité).
Supervision / « savoir si c’est up » comme besoin principal « On veut juste voir l’état des services » Ce n’est pas le cœur d’une mission. Demander quel flux / quel métier derrière ; sinon risque de hors positionnement.
Front / UX dominant « Refonte du portail + un peu d’intégration » Extraire un lot backend/flux ou décliner le front
Pas d’interlocuteur technique Achats ou direction seule Conditionner à un référent SI
Périmètre trop large « Tous les sites, tous les flux » Lot 1 = un site / un connecteur
Astreinte / délais extrêmes « Intervention en cinq minutes, 24×7 » Hors Phase 0 sauf canal et horaires explicitement bornés
Grosse console métier de règles « Les users doivent tout configurer eux-mêmes dans une UI » Bornage : config d’exploitation vs produit applicatif
Accès ou exemples absents « Les APIs, on verra plus tard » Pas de devis ferme
Enrichir le socle sans livrable clair « D’abord le framework, ensuite le métier » Uniquement si un livrable client reste net

Rouges

Écarter ou reformuler

SignalExemplePourquoi
Régie / renfort d’équipe « Deux développeurs pendant six mois chez nous » Pas de livrable forfait
Achat de licence / support d’un framework « On veut votre socle / votre produit tel quel » On vend le résultat, pas le framework
Refonte applicative générale « Réécrire toute l’application métier » Hors cœur intégrations / petite plateforme backend
Mission sans levier Script jetable, hors flux, hors industrialisation Ni exploitation ni enrichissement du système de production
Observabilité SI globale comme objet unique « Remplacez notre stack de monitoring d’entreprise » Hors offre
Mobile, pure UI, data platform comme cœur Application store, design system seul, entrepôt décisionnel Sauf petit connecteur d’alimentation clairement borné
Fourniture de profils « Vous staffez, on manage » Contradiction avec concepteurs = développeurs
